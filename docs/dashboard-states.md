# Dashboard 状态与显示规则

看板把 GitHub 事实与 Keel 流程证据分开显示。不同时间的请求不是原子快照，不能把“刚刷新”理解为整个流程刚有活动。

## 列表与界面

| 场景 | 预期显示与行为 |
|---|---|
| 首次加载、还未读到PR | 正在同步；不展示挤在一起的阶段头或虚构卡片 |
| 当前范围确实没有PR | 明确空状态；可切换进行中/历史范围 |
| 全部有PR，但自动推进/需要我/搜索筛选结果为0 | 没有匹配的PR；保留全局数量与筛选入口；阶段头不重叠 |
| 有匹配结果 | 宽屏三列，窄面板单列；卡片208px，步骤线92×3px，步骤号在线左 |
| 只有前几页 | 标明已读取数量和分页未结束；未读完不删除旧卡 |
| 帧缺行或格式不完整 | 保留旧卡，标为待恢复，不把少量数据误认为完整列表 |
| 网络断开/请求超时 | 保留上次数据并显示错误；停止循环动画，稍后重试 |
| 局部交接/关联PR不可读 | 受影响卡片标待确认，整轮保持partial；不因后页正常就消除警告 |
| 账号改变 | 先隔离旧账号；旧缓存、迟到本地更新不能重新改写新账号 |
| 历史范围 | 可以显示已合并/已关闭；这两种终态不计为自动推进 |
| 隐藏/返回 | 隐藏停止后续查询，返回请求刷新；配额退避仍优先 |

## 卡片状态

| 事实或证据 | 显示 | 是否计入自动推进/需要我 |
|---|---|---|
| GitHub MERGED | 已合并 | 都不计入 |
| GitHub CLOSED | 已关闭 | 都不计入 |
| 有有效当前交接 | 已交接；只显示已知交接阶段，不编造mini内部进度 | 都不计入 |
| 主控明确的 `human:*` 门 | 等待你的决定 | 需要我 |
| 普通Agent决策门（如g-accept） | 等待主控裁决 | 有run时计入自动推进，不计入需要我 |
| 当前节点在途，有90秒内实际派发、对账或步骤回报 | 当前执行节点/步骤 | 自动推进 |
| 在途证据过期或未知 | 活动待确认 | 都不计入 |
| 等待CI或后续推进，有对应run | 等待继续推进/具体等待事项 | 自动推进 |
| Keel停止 | 工作流已暂停 | 都不计入 |
| Keel当前这一轮结束，但PR仍OPEN | 本轮已结束，不等于已合并或可合并 | 都不计入 |
| GitHub有PR，本机没有关联run | 只显示GitHub事实，步骤未知 | 都不计入 |
| 同一个PR有多轮run | 按明确关联和创建代际识别当前run；旧run被查询不能抢走关联 | 取当前run状态 |

## 步骤与新鲜度

- 普通 `keel_wait` 或刷新GitHub不算Worker心跳。工作流版本时间与活动证据时间是两个字段。
- 当前派发的对账时间与有效步骤回报时间取较新的真实证据；旧步骤不能让刚核实的活动变旧。
- 等待 `pr_open` 时显示本地“整理提交并推送”，不能用旧提交CI全绿把步骤跳到交接。
- 旧HEAD的流程步骤不当作当前提交进度；迟到本地事件不能把新HEAD/已合并状态覆盖回旧数据。
- 交接使用与车道相同的当前判定。配置Vigil时按当前归属/Ready代次核对，不仅靠旧文件存在，也不能仅凭HEAD变化撤销同代次交接。

## 查询与额度

调用运行插件电脑上的 `gh api graphql --hostname github.com`，复用gh有效的用户授权。本人作者PR跨仓分页，每页50条；本机已关联的其它PR补查。卡片CI明细只取前20项，整体状态读取GitHub rollup；超过20项明确标记明细不完整。

可见时一轮完成后等待30秒；未完成页通常650ms后续读。个人GraphQL额度通常为每账号每小时5000点，非每台电脑各5000次；真实cost与限额以返回为准。详情、交接检查、关联补查和其它客户端会额外消耗额度。数据不全、配额不足或网络问题不得被显示为“全部通过”。
